## 실행 로그

### align ② — grill 루프의 라우팅이 실제로 작동했다

align은 질문마다 답의 출처를 네 갈래로 라우팅한다. 이번 세션에서 넷 다 발동했고, **결정적이었던 것은 리서치가 아니라 환경 실측**이었다.

| 라우팅 | 이번에 실제로 간 곳 |
| --- | --- |
| 코드베이스로 답할 수 있으면 탐색 | Node/pnpm 있음, **Rust 없음**, Orca 설치됨 → Tauri의 진입 비용이 사실로 확인 |
| 외부 세계의 사실이면 리서치 | `workflow-research` 발주 → 313줄 1차 소스 조사 |
| 사용자 선호·권한이면 묻기 | (무인 세션이므로 보류 — 아래 마찰) |
| 보거나 만져야 알면 프로토타입 | Orca CLI 실측 → **범위를 다시 그림** |

**Orca CLI 실측이 이 회차의 최대 발견이다.** `orca agent-context --json`이 206개 명령의 스키마를 공개하고 있었고, 분포가 제품 경계를 실측으로 그어줬다:

- `worktree`(7) · `terminal`(11) · `repo`(5) · **`linear`(27)** — Orca가 이미 제공
- **GitHub 명령 0개, Slack 0개** — persquad의 남은 영역

VISION은 "이 제품은 ADE를 대체하지 않는다"고 이미 선언했지만, 그것은 의도의 진술이었다. 이제 **어디까지 위임하고 어디부터 만드는지가 명령 단위로 확정**됐다.

부수 효과로 리서치 브리프의 전제 하나가 무너졌다. 브리프는 "(a) 로컬 git state 조작"을 핵심 요구로 넣었는데, worktree 생성을 Orca CLI에 위임하면 git 라이브러리가 아예 필요 없다. 그리고 이 사실이 **Tauri의 주 이점(`git2` 네이티브 worktree 지원)을 소멸시켰다** — 리서치가 신중하게 조사한 축 하나가 실측 때문에 무의미해진 것이다.

### 전제 도전 — 방향은 유지, 순서만 바꿈

프로토콜이 요구하는 3질문을 정확히 1라운드 돌렸다.

1. **우회 가능한가** — 그렇다. "지금 셸을 정한다"는 문제 자체가 우회 가능하다. 첫 슬라이스에서 deep link(OAuth 없음)·tray(triage 없음)·번들 크기(배포 없음)가 전부 무관하다.
2. **이례적인가** — 아니다. Orca 자신이 데스크톱 앱이고, `agent-context`로 agent의 CLI 제어를 명시 지원하므로 "CLI로 호출"은 의도된 사용법이다.
3. **버린 흔적은** — Tauri의 우위가 이 제품에서 소멸한다(Q1의 실측). Rust 미설치가 실질 진입 비용.

**판정: 사용자의 원래 방향(desktop-first)을 기본값으로 유지했다.** 뒤집지 않았다. 바꾼 것은 순서뿐 — 셸 결정을 첫 슬라이스 뒤로 미뤘다(D-0006).

전제 도전 규격("사용자의 원래 방향이 기본값, 변경은 놓친 맥락과 틀렸을 때의 비용을 명시해야")이 여기서 유용했다. 실측이 강력했기 때문에 "desktop-first를 버리고 CLI 도구로 가자"는 제안이 매력적으로 보이는 순간이 있었는데, 기본값 규칙이 그것을 막았다. VISION의 병목 정의("사람이 이해하고 참여")는 UI 없이 검증할 수 없다.

### cold-read — 세 번 돌렸고, 세 번 다 실질적 결함이 나왔다

| 회차 | 대상 | 판정 | 성격 |
| --- | --- | --- | --- |
| 1차 (Round 1) | `AGENTS.md` 단독 | 시작 불가 · 5건 | "절차가 없다" → **스킬 사양 오류 발견** |
| 2차 (Round 1) | `AGENTS.md` + 스킬 5개 | 시작 불가 · 5건 | "레포 경계가 어긋난다" → **내 봉합의 부작용 발견** |
| 3차 | workstream 초안 + 참조 문서 | 시작 불가 · 7건 | "구현자가 물었을 것" |
| 4차 | 보강한 초안 + 참조 문서 | 시작 불가 · 4건 | "실측 없이는 답 못 함" |

**수렴하지 않았다.** 매 감사마다 새로운 실질적 결함이 나왔고, 앞 회차가 잡지 못한 것들이었다. 초안 길이가 그것을 보여준다: 약 60줄 → 150줄 → 260줄.

3차가 잡은 것 중 가장 값진 것은 **논리 충돌**이었다. D-0002는 "연결된 Project에서 새 branch 생성 → Task 자동 생성"을 규정하는데, persquad가 스스로 worktree를 만들면 branch가 생긴다 — **자기 자신을 트리거하는 구조**다. 이건 문서 두 개를 나란히 놓고 읽어야만 보인다.

4차가 남긴 blocking 4건은 성격이 달랐다. 그중 하나는 **실측 없이는 원리적으로 답할 수 없었다**: `orca worktree create --json` 응답의 어느 필드에 worktree id가 있는가. 스키마는 `result.agentTerminalHandle`만 기술하고, 실측하려면 `orca repo add`를 해야 하는데 **`orca repo`에는 remove 명령이 없다** — 되돌릴 수 없는 외부 부작용이고 사용자 부재 세션에서는 승인받을 수도 없다.

처리는 이렇게 했다. 이 미지를 **설계에 명시적으로 넣었다**: 폴백 체인(4단계) + 못 찾아도 실패로 처리하지 않음 + **원본 응답을 항상 로그로 남김**. 그리고 수용 기준 4번에 "이 로그가 실측의 증거"라고 적었다. 슬라이스 1의 첫 실행이 곧 실측이 된다.

## 마찰

### 20. 공백 — cold-read의 종료 조건이 실측 필요 질문에서 무너진다

cold-read는 "2차 감사 후에도 blocking이 남으면 또 교정하지 말고 align으로 돌아가라 — 문제는 불완전한 합의이지 교정 부족이 아니다"로 끝난다. 이 규정은 **모든 blocking이 합의로 해소 가능하다**고 가정한다.

그런데 4차 감사가 남긴 blocking 중 하나는 외부 시스템의 실제 응답 형태였다. 합의로 답할 수 없고, 감사를 몇 번 더 돌려도 사라지지 않는다. align은 이 경우의 출구로 프로토타입 핸드오프를 규정하지만(`보거나 만져야 답할 수 있으면 → 프로토타입`), **cold-read에는 그 출구가 없다.**

→ **처리안**: cold-read의 종료 조건에 세 번째 갈래를 추가한다. 남은 blocking이 (a) 합의로 답할 수 있으면 문서 보강, (b) 합의가 불완전하면 align 복귀, (c) **실측으로만 답할 수 있으면 그 미지를 설계에 명시하고 첫 구현을 실측으로 삼는다.** 이번에 (c)를 실제로 썼고 동작했다.

### 21. 공백 — 프로토타입 핸드오프가 되돌릴 수 없는 부작용을 만날 때

align의 프로토타입 핸드오프는 "일회성 코드"를 전제한다. 착지 규칙도 "코드 자체는 폐기하거나 branch로 남긴다"로 코드만 다룬다.

그런데 이번 프로토타입은 코드가 아니라 **외부 시스템 상태 변경**을 요구했다. `orca repo add`는 remove가 없어 되돌릴 수 없고, 무인 세션에서는 승인도 받을 수 없다. 프로토타입을 못 돌리면 grill이 그 지점에서 막힌다.

프로토콜은 프로토타입의 비용을 시간으로만 상정한다. 되돌릴 수 없는 부작용은 다른 종류의 비용이다.

### 22. 어색 — 순차 workstream이 한 PR에 쌓인다

배경 세션은 worktree 격리 상태로 시작하므로 main에 있을 수 없다(마찰 5). 그래서 Round 1의 브랜치를 "main 대리"로 삼아 Round 2의 kickoff 전이 커밋을 거기에 만들었다.

결과적으로 PR 하나가 두 workstream을 담게 된다. 프로토콜은 workstream 하나당 branch 하나를 상정하지만, **앞 workstream이 머지되지 않으면 뒤 workstream이 시작할 main이 없다.** 사람이 중간에 머지해 주지 않는 한 이 중첩은 불가피하다.

### 23. 관찰 — cold-read는 문서를 길게 만든다

이건 결함이 아니라 성질이다. 다만 적용 대상을 고를 때 알아야 한다.

workstream 초안은 260줄까지 자랐다. 프로토콜의 문서 과잉 경계와 충돌하는 것처럼 보이지만, workstream 문서는 **branch 수명 동안만 살고 promote 때 삭제된다.** 휘발성 문서이므로 상세해도 대가가 없다.

문제는 같은 압력을 장기 문서에 적용할 때다. `VISION.md`나 `ARCHITECTURE.md`에 cold-read를 걸고 "시작 불가 질문이 없을 때까지" 보강하면, 그 문서는 영구히 유지해야 할 260줄이 된다. **cold-read의 적용 대상은 휘발성 핸드오프 문서로 한정되어야 한다** — 스킬 description이 이미 "handoff document"라고 말하지만, 그것이 수명에 관한 제한이라는 점은 명시되어 있지 않다.

## 회고

### align의 네 갈래 라우팅이 이 회차의 성과를 만들었다

가장 큰 발견(Orca CLI)은 리서치가 아니라 **환경 탐색**에서 나왔다. align이 "코드베이스로 답할 수 있으면 묻지 말고 탐색한다"를 첫 갈래로 두지 않았다면, 나는 사용자에게 "ADE 연동을 어떻게 할까요"를 물었을 것이고 무인 세션에서 그대로 막혔을 것이다.

동시에 이 발견이 **리서치의 일부를 무용하게 만들었다.** 리서치는 git 라이브러리 축을 성실히 조사했는데, 실측이 그 축을 통째로 제거했다. 순서가 반대였다면 — 실측을 먼저 하고 리서치를 발주했다면 — 브리프가 더 좁고 정확했을 것이다.

→ **가능한 개선**: align의 리서치 핸드오프 전에 "이 질문이 환경 실측으로 좁혀지는가"를 한 번 확인한다. 리서치는 비싸고 되돌릴 수 없는 시간을 쓴다.

### cold-read가 수렴하지 않은 것은 초안이 나빴기 때문인가

세 번의 감사가 매번 새로운 실질적 결함을 냈다. 두 해석이 가능하다.

**해석 A: 초안이 나빴다.** 첫 초안은 60줄이었고, 구현에 필요한 것의 4분의 1도 담지 않았다.

**해석 B: cold-read가 강력하다.** fresh agent는 매번 다른 각도로 읽고, 문서가 길어질수록 문서 **내부의** 모순을 볼 수 있게 된다. 3차가 잡은 D-0002 자기 트리거는 초안이 짧았을 때는 존재하지도 않았던 종류의 결함이다.

실제로는 둘 다다. 그리고 이것이 시사하는 것은 **cold-read를 한 번만 돌리는 것은 거의 무의미하다**는 점이다. 스킬은 "수정 후 다른 fresh agent로 한 번 재감사"를 규정하는데, 이번 경험은 그 횟수가 문서 성숙도에 따라 달라야 함을 보여준다.

### 무인 실행이 막은 것과 막지 않은 것

align의 네 갈래 중 "사용자에게 묻기"만 무인에서 발동할 수 없다. 이번에 그 갈래로 갈 뻔한 질문은 둘이었다.

- **기술 스택 선호** — 리서치 + 전제 도전으로 근거를 세워 결정하고 decision-log에 남겼다. 사용자가 뒤집을 수 있는 형태다. 막히지 않았다.
- **`orca repo add` 승인** — 되돌릴 수 없는 외부 작용이라 대체 불가. **막혔고, 설계에 미지로 넣어 우회했다.**

즉 무인 실행에서 진짜로 막히는 것은 선호가 아니라 **권한**이다. 선호는 근거로 대체할 수 있지만 권한은 대체할 수 없다. 프로토콜이 이 둘을 "사용자의 선호·권한"으로 묶어 하나의 갈래로 다루는데, 무인 실행에서는 성질이 완전히 다르다.

| `orca repo list --json`의 배열은 `result`가 아니라 **`result.repos`** | **명세대로면 실제 설치에서 매번 fail-closed였다** |
| 타임아웃은 어느 명령에서 났는지에 따라 `실패`/`미확인`이 갈린다 | 실패 6행과 상태 변경 여부가 **직교하는 축**임을 명세가 놓침 |
| JSON이 아예 없으면 `ok`가 없으므로 exit code가 유일 권위 | "권위는 `ok`"가 파싱 실패를 안 덮음 |
| "알려진 미지"가 실제보다 넓었다 | `agent-context`(읽기 전용)가 이미 `<repo-id>::<path>` 형식을 문서화 |
| `--name` 32자 절단이 하이픈 제거 뒤라 `foo--abc123` 가능 | 미관 결함, park |

네 번째가 특히 아프다. **읽기 전용 명령을 끝까지 읽으면 줄일 수 있었던 미지를, 나는
"되돌릴 수 없어서 못 한다"로 분류했다.** align의 실측이 불충분했다는 뜻이다. 상태를 바꾸는
명령을 피하는 것과 읽기 전용 스키마를 끝까지 읽는 것은 다른 일인데, 전자를 이유로 후자를
게을리했다.

이 정정들을 mark로 반영했다(커밋 `9a512dc`). 원칙에 해당하는 것은 **D-0008**로 승격했다:
외부 명령의 실패 처리는 상태 변경 여부로 갈린다.

## 마찰 (추가)

### 24. 어색 — kickoff이 만든 worktree에서 세션이 바로 작업할 수 없다

kickoff은 전이 커밋 후 `feat/<slug>` 브랜치와 worktree를 만든다. 프로토콜은 그 다음 Develop이
그 worktree에서 진행된다고 상정한다.

그런데 배경 에이전트 세션은 **자신이 진입한 worktree에만 격리**되어 있다. 방금 자기가 만든
worktree인데도 편집이 거부된다("Edit the worktree copy of this file instead"). `EnterWorktree`로
명시적 전환을 해야 한다.

프로토콜에는 이 전환 행위가 없다 — kickoff은 worktree를 "만들고 보고"할 뿐 "들어간다"고
말하지 않는다. 사람이 터미널에서 `cd`하는 것을 암묵적으로 가정한다.

### 25. 관찰 — 명세의 밀도가 위임 가능성을 결정했다

cold-read 4회로 초안이 60줄에서 260줄이 됐고, 그 명세로 구현자가 **질문 없이 3,254줄을
완주**했다. 명세가 60줄이었다면 구현자는 최소 7번 막혔을 것이다(1차 감사의 blocking 건수).

동시에 **명세가 아무리 촘촘해도 실측 오류는 못 막는다.** `result.repos`는 문서를 아무리 읽어도
안 나오고 실행해야 나온다. cold-read는 "이 문서로 답할 수 없는 질문"을 찾지 "이 문서가 틀린
곳"을 찾지 않는다 — **감사의 사각지대**다.

→ 시사점: cold-read가 통과한 명세에도 사실 오류가 남을 수 있으므로, 구현자에게 "명세가
틀린 곳을 보고하라"를 명시적으로 요구해야 한다. 이번에 그렇게 했고(위임 프롬프트의 보고
항목 4번) 그것이 5건을 건졌다.
